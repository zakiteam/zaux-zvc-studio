# Dev mode and PHP export

## Dev mode

Fourth editor mode next to Design mode, Design tokens and Theme editor (`BuilderModeSwitcher`, `workspaceView === 'dev'`). It is the design view itself (`BuilderDesignView`: canvas, workspace tabs, templates, outline, viewport and zoom) with the design options removed and the Inspector replaced by `BuilderDevPanel.vue`.

- Read-only through the existing edit gate: `canEditRemote` is false in Dev mode, so `commit`, undo/redo and every control gated by it refuse changes (`zx_builder_dev_readonly`). Remote saves and project actions follow the role only (`remoteWritable`), so pending saves still flush.
- Navigation and selection stay: templates (sidebar pages and header breadcrumb), workspace tabs, outline and canvas selection, zoom, viewport, CSS inspector, preview toggle. Dev mode allows only view/navigation/export layout shortcuts (`DEV_LAYOUT_ACTIONS` in `useBuilder.js`).
- Hidden or disabled: Library and Elements tabs, outline copy/paste/sync/reset/group tools, row duplicate/delete, instance rename, free drop zone, body background, command palette, Quick style. The node context menu keeps selection, folding and export items (`DEV_MENU_ITEMS`). The canvas receives `readonly`: selection, hover outline and toolbar name stay, drag, drop and node actions do not.
- `BuilderDevPanel`: scope tabs **Element / Component / Page** (follows the selection), details (tag, classes, children, fields read, export name, source, ZVP used, own CSS, page component list that selects on click), data contract and export with copy/download:
  - Element: Zaux JSON (rendered, `nodeRuntime`), compact JSON (`nodeDocument`), Vue markup (`vueNodeMarkup`), PHP array (`phpNodeSnippet`).
  - Component: Zaux JSON, editable JSON, JS package, Vue SFC, PHP (with usage snippet).
  - Page: Zaux JSON, editable JSON, JS package, PHP.
- A placed component exports with its page values as defaults (`definitionWithData` in `domain/export.js`, shared with the export dialog); the JS package uses the shared `componentPackageFiles` (`app/services/starter-export.js`).

## PHP export (`domain/php/`)

PHP is an export format, the counterpart of the JavaScript ZVC/ZVP export, written for WordPress themes based on **zaux-wp-core** (parent theme) and its child themes (e.g. **zaux-wp-project**). The generated files rely on what that theme already provides; the export never ships or invents runtime helpers.

### Target theme contract (zaux-wp-core)

Reference projects (user machine): `C:\Users\Carlo\Local Sites\zaux-wp-theme\app\public\wp-content\themes\zaux-wp-core` (parent) and `...\zaux-wp-project` (child). Re-read their `AGENTS.md`, `app/helpers/components/Components.helper.php` and the sample components in `zaux-wp-project/components/base/` when the contract changes.

- `components/base/{name lowercase}/{Name}.zvc.php` defines `ZVC{Name}($data = [], $params = [])`; `components/_partials/{name lowercase}/{Name}.zvp.php` defines `ZVP{Name}(...)`. The folder must be the lowercase file name and names are unique across `base` and `_partials`.
- `ZauxComponentsHelper::autoLoadComponents()` requires every component on `after_setup_theme`: generated files never `require` anything, and every function is callable from templates and from other components.
- `{Name}.meta.php` and `data/{Name}.defaults.php` `return` arrays, read with `ZauxComponentsHelper::getMeta()` / `getDefaults()` (never `include`d by the component).
- `ZauxComponentsHelper::getValue($data, $path)` (exact key, then dot path, null when missing) and `renderNode($nodeObject, $data, $params)` (`meta` + `node`, as `ZVCHelper.renderNode`).
- Pages collect nodes and call `ZauxComponentsHelper::printComponentsList($components)`; the child `header.php` prints `<div id="app"></div>`.
- Every PHP file starts with `defined("ABSPATH") || exit;`; translatable labels use `__()` with text domain `zaux`.
- ACF bridges `{Name}.acf.php` (ZVC only) return `["layout" => ["sub_fields" => [...]], "map" => fn($data, $context)]`, read by `ZauxACFHelper` for the flexible content fields declared with the `zaux_acf_flexible_fields` filter. Sub field names are the component `$data` keys; ACF keys are generated by the theme.
- Overrides (`components/overrides/...`) belong to the theme project; the export does not generate them.

### Output

Layout (user choice, 2026-10-21), the same in every PHP export and for both ZIP download and file system writes: one folder per ZVC directly at the root (`hero/`, `splitsection/`: their place is the theme `components/base/`), partials in `_partials/<name>/` (theme `components/_partials/`), page templates in `page-templates/` (theme root). No `components/base/` wrapper.

| JavaScript | PHP |
| --- | --- |
| `Hero.zvc.js` / `Card.zvp.js` | `hero/Hero.zvc.php` (`ZVCHero`) / `_partials/card/Card.zvp.php` (`ZVPCard`) |
| `Hero.meta.js` | `Hero.meta.php` (`label`, `ZVCName`/`ZVPName`, `meta.version`, `fields`; labels in `__()`) |
| `data/Hero.defaults.js` | `data/Hero.defaults.php` |
| `data = { ...defaults, ...data }` | `$data = array_merge(ZauxComponentsHelper::getDefaults("Hero"), $data);` |
| `gv('key')` | `$gv('key')` (closure over `ZauxComponentsHelper::getValue`) |
| `ZVCHelper.renderNode` | `ZauxComponentsHelper::renderNode($nodeObject, $data, $params)` |
| ZVP reference + `resolve-partials.js` | `ZVPCard([...props], $params)` wrapped in `ComponentsRenderer` (also inside defaults and page data) |
| `style/Hero.css` | `style/Hero.css` (not loaded by the theme: move it into the Zaux bundle) |
| — | `Hero.acf.php`: ACF Flexible Content bridge of a ZVC (included by default, `options.acf: false` excludes it) |
| Template | `page-templates/<name>.php`: `Template Name` header, `get_header()`, `$components = [ZVCHero([...]), ...]`, `printComponentsList`, `get_footer()` |

The entry function follows the zaux-wp-project samples (`SplitSection.zvc.php`): `$meta` (ZVC only), `$data`, `$gv`, `$nodeObject` with `"meta" => ["ZVCName" => $meta['ZVCName']]` (ZVC only, like the JS export) and `"node"`, then `renderNode`. `<Name>` is the export name without `ZVC`/`ZVP`, sanitized to letters and digits, with a numeric suffix when taken (case-insensitive, shared by ZVC and ZVP); the function is `ZVC<Name>`/`ZVP<Name>` and the meta `ZVCName`/`ZVPName` matches it, as in the Zaux starter package. `README.md` is opt-in (`options.readme`, unchecked by default); ACF bridges are included unless unchecked (`options.acf`, checkbox **Include ACF bridge** in the export dialog, PHP package options, Dev panel and PHP conversion page; the Inspector Code tab shows only the entry file). Callers build the options with `phpExportOptions()` (`app/services/php-export.js`), which also passes the ZButton themes of the Zaux release to the profile (`acf.buttonThemes`).

### ACF bridge (`{Name}.acf.php`)

Generated for ZVCs only (ZVPs never become layouts), in the format of `zaux-wp-project/components/base/splitsection/SplitSection.acf.php`: `$defaults = ZauxComponentsHelper::getDefaults(...)`, `layout.sub_fields` (labels in `__()`, no layout label: `ZauxACFHelper` uses the meta label) and `map` (`use ( $defaults )`). Field mapping (`profile.acf.fields`, by Studio field type):

| Studio field | ACF sub field | `map` |
| --- | --- | --- |
| `text` / `textarea` / `html` | `text` / `textarea` (`new_lines` empty) / `wysiwyg`, `default_value` from the defaults | — |
| `number` | `number` | numeric string → number, empty → default |
| `switch` (`boolean`) | `true_false` (`ui`) | → bool |
| `select` | `select` with the field options (`allow_null`) | empty → default; non-string option values restored |
| `image` | `image` (`return_format` url) | empty → default |
| `media` | `image` (url) | url → `{ type: img, props: { src } }` over the default media |
| `button` | `group`: `link`, `theme` (select of ZButton themes), `iconName` (select of `ZauxUIHelper::getIconSetAsList()`) | → ZButton props over the default CTA; no link → default |
| `buttongroup` | `repeater` of the same sub fields | → list of ZButton props, rows without link skipped |
| `json`, `component`, `css-editor`, others | none (listed in the file header) | keep the defaults |

Field conditions (`showIf`) are not converted: ACF conditional logic needs the generated field keys, which depend on the flexible content field name.

Where it appears:
- Export dialog: format **PHP** for the current component and the current template (file explorer + ZIP), and scope **Zaux PHP package** (`BuilderStarterOptions variant="php"`, same ZVC/ZVP/template selection as the starter package).
- Node context menu: **Export ZVC (PHP)** (`export-php`).
- Inspector **Code** tab: **PHP** view of the entry file.
- Dev mode panel: component and page packages, usage snippet, PHP array snippet for a single element.
- Hub **PHP conversion** page (`/php-converter`): a project's `components/virtual` folder from a ZIP upload or from the file system (below).
- **Write to theme** next to every PHP download: writes the files into a zaux-wp-project theme folder (below).

### Writing into a theme folder

Every PHP export can also be written straight into a folder of a zaux-wp-project theme (zaux-wp-core child theme), normally its `components/base/`, besides the ZIP download. The files keep the export layout (same as the ZIP): **Write to theme** (`BuilderPhpThemeWrite.vue`) in the export dialog (PHP component/template/package), the Dev panel (PHP packages) and the PHP conversion page.

- `app/services/php-theme.js` (browser IO): File System Access API `showDirectoryPicker({ mode: 'readwrite' })` (Chromium on a secure context), reads and writes through the `zaux-bridge.js` helpers inside the granted folder only. The folder is remembered for the session (module variable, never persisted); **Change folder** picks another one.
- `domain/php/theme.js` (pure): `themeTargetNotes` warns when the folder is a theme root (`style.css`) or is not named `base`, and notes that `_partials/` must be moved to `components/_partials/` and `page-templates/` to the theme root (writing stays possible); `themeFiles` leaves `README.md` out, `themeWritePlan` compares with the files on disk: new, overwrite, unchanged (not written).
- A confirmation modal lists every file with its status before writing; paths are the export paths relative to the chosen folder (`<name>/...`, `_partials/...`, `page-templates/...`). Files that are on disk but not in the export are never deleted.

### PHP conversion of a components/virtual folder (ZIP or file system)

`app/pages/php-converter.vue` (hub navigation) takes the `components/virtual` folder of a Zaux project and returns the PHP files in the same layout, with the file explorer and a ZIP download. Sources (`virtualSources` in the service, `{ kind, name, read() }`, never persisted):
- **ZIP**: file input or drop.
- **Folder** (`Choose folder`): File System Access API `showDirectoryPicker({ mode: 'read' })` (Chromium on a secure context) or a dropped folder (`getAsFileSystemHandle`). A project root or a `components` folder is narrowed to `components/virtual`; hidden folders, `node_modules`, `docs`, `dist` and `vendor` are skipped. **Convert again** re-reads the folder from disk, so edits in the project are picked up without choosing it again.
- **Folder fallback**: where the API is missing, an `<input webkitdirectory>` reads the chosen folder once (Convert again reuses that snapshot).
- **GitHub repository** (source switch *GitHub repository*, `BuilderGithubSource.vue`): token + organization (default: owner of `package.json#zaux.repository`, i.e. `zakiteam`; user accounts work too) → repository list with search → branch (default branch first) → `components/virtual` folder found in the branch tree (`virtualRoots`: `project/components/virtual/` first, then e.g. `core/components/virtual/`). Read only: `app/services/github-source.js` makes only GET requests to `api.github.com` (repos, branches, recursive git tree, raw contents). The virtual folder files are downloaded up front (8 at a time); any other file is fetched when a module imports it, and `@zx_project/` resolves to the project folder of the repository (e.g. `project/components/shared/.../X.meta.js`) before the Studio bundled modules; `@zx_core/` and `@zx_style/` keep resolving to the Studio bundled Zaux. **Convert again** re-reads the branch (latest commit). Token, two modes:
  - **Server token** (default when configured): `ZAUX_REPO_BROWSING_GITHUB_TOKEN` in `.env` / the hosting environment (or `NUXT_REPO_BROWSING_GITHUB_TOKEN`, `runtimeConfig.repoBrowsingGithubToken`, server only). The browser calls `GET /api/github/proxy?path=…` with its Supabase session (`server/utils/session.js` `studioSession`: valid user, active profile, shared with the media routes); `server/utils/github.js` forwards only the whitelisted GET endpoints (`orgs|users/{owner}/repos`, `repos/{o}/{r}/branches`, `git/trees/{ref}`, `contents/{path}`, whitelisted query keys, raw contents as text). `GET /api/github/status` tells whether the token is configured, never the token. The token never reaches the browser.
  - **Personal token** (*Use a personal token*, or when the server has none): typed in the page, sent straight to `api.github.com`, kept in memory or in `sessionStorage` for this tab when *Remember the token* is checked.
  The build token `ZAUX_GITHUB_TOKEN` is never used here. The repository code runs in the page like any other source: with the server token it can at most read repositories through the proxy during the session; a personal token should be fine-grained and read-only (Contents + Metadata).

- `app/services/php-converter.js` (browser IO): reads the source (JSZip, directory handle walk, file list or GitHub tree) into an archive (`archiveFrom`: `root`, `projectRoot`, `sources`, `has(path)`, async `text(path)` for on-demand files), finds the virtual root (`components/virtual/`, `virtual/` or the ZIP root) and every `*.zvc.js` / `*.zvp.js`. Each file becomes an ES module from a blob URL: relative imports and `@zx_project/components/virtual/...` resolve to the ZIP files (`.js`, `.json`, `/index.js`), styles become empty modules, other `@zx_core` / `@zx_project` / `@zx_style` imports resolve to the Zaux modules bundled with the Studio (lazy `import.meta.glob`: helpers, component metas, virtual components, `ui.config`). Unresolved imports fail only for the component that loads them. Defaults come from `data/<Name>.defaults.js`; ZVC names are normalized like `integrations/zaux/source-library.js`.
- `domain/php/sources.js` (`phpSourceExport`): the same pipeline as the Studio library — `definitionFromSource` → `capturePartials` (ZVP references between the uploaded components) → `phpDefinitionsExport` (`phpModel`, sentinel bindings, profile templates) — with the modules visible to the source registry only during the call (`withSourceModules` in `domain/source-runtime.js`). Failures are reported per file (`errors`) and do not stop the others.
- Nothing is persisted or sent to the server. The uploaded JavaScript runs in the Studio page (the UI says to upload only trusted projects).

### Where to retouch the output

| File | Role |
| --- | --- |
| `profile.js` | **The place to change the PHP.** Naming (`component`, `function`, `page`), theme paths, text domain, value expressions (`$gv` bind and spread), meta content, root and partial shapes, text templates of the entry, meta, defaults and page files. Templates receive prepared pieces `p` (names, `p.php(value, depth)`, `p.data`, `p.string`, `p.comment`, `p.indent`). Bump `version` when the contract changes (now 2). |
| `emit.js` | Prepares the pieces, turns ZVP references into `ZVP<Name>()` calls (`withPartialCalls`), builds the ACF bridge pieces (`acfPieces`) and writes the files of a unit; README text. |
| `model.js` | Workspace definition → JSON model (`exportName`, `kind`, `fields`, `defaults`, compact `nodes` with `$bind`/`$spread`, `partials`, `css`, `native`, `snapshot`). |
| `bindings.js` | Field markers for native (JavaScript) definitions (sentinel render, verified). |
| `printer.js` | JSON → PHP literal: literals stay literal (false, 0, '', null); `$bind`/`$spread` → profile expressions; `PhpCall`/`PhpCode` for emitter-made calls (`ZVPCard(...)`, `__()`, `$params`); strings always quoted, control characters escaped. |
| `index.js` | Assembly and API: `phpComponentExport`, `phpTemplateExport`, `phpProjectExport`, `phpDefinitionsExport`, `phpNodeSnippet`; options `readme`, `acf`. |
| `sources.js` | `phpSourceExport` for uploaded native modules. |

Semantics mirror the JS runtime: `array_merge(defaults, $data)`, exact key then dot path (`getValue`), `$spread` merges an array field over the fallback props (`array_replace`), empty JSON objects as `(object) []` so `wp_json_encode` keeps `{}`. Equal copies share one component; different copies with the same export name get a numeric suffix (instances are independent copies). Native (JavaScript) ZVC/ZVPs have no markers because their tree comes from `buildNode(data)`: `bindings.js` renders the module with sentinel field values, turns intact sentinels into `$bind` and spread object fields into `$spread`, and keeps the result only if, resolved with the real data, it equals the real render exactly. Fields used in conditions, concatenations or transformations stay literal; the JS logic itself is not translated (noted in the file header). Without the module the stored projection (ZVC) or a runtime snapshot (ZVP) is used.

Not generated: flexible content declarations (`zaux_acf_flexible_fields`), ACF conditional logic, overrides, server-side HTML rendering. Integer-like keys become PHP integer keys.
